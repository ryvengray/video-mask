# 视频隐私打码平台部署架构与运维说明

## 1. 面向客户的部署结论

平台采用“**一台 Controller（内置 Autoscaler）+ 多台 GPU Worker + 对象存储**”的横向扩展架构：

- Controller 负责创建、分配和追踪任务，并提供任务看板；
- 每台 Worker 使用 GPU 独立处理视频，可随业务量增加或减少；
- 源视频和成品视频保存在客户指定的对象存储中，视频不经过 Controller 中转；
- Autoscaler 与 Controller 部署在同一台控制机，根据待处理队列和空闲时长按需启动或停止已授权的云端 GPU Worker；
- Ansible 负责对 Controller 与所有 Worker 进行统一、可重复的安装、升级和服务管理。

完整架构图请在浏览器中打开：[部署架构图.html](./部署架构图.html)。图中以更大区域展示了 Autoscaler 对运行中和待机 GPU Worker 主机池的动态扩缩容控制。

> Controller、Autoscaler 与 Ansible 控制节点部署在同一台服务器。三者职责独立：Controller 管理任务，Autoscaler 管理已授权的 Worker 云主机启停，Ansible 管理机器的软件与服务版本。

## 2. 处理流程

```text
1. 上传源视频至对象存储指定目录
2. Controller 创建待处理任务（支持 API、Web 或存储扫描入队）
3. 空闲 Worker 主动领取匹配的任务
4. Worker 直接下载源视频至本地临时工作目录
5. GPU Worker 执行选定的打码算法（当前集群默认仅人脸）
6. Worker 直接上传成品视频至对象存储
7. Worker 上报校验结果、处理进度与完成状态
8. Controller 在看板中保留任务、Worker 与失败重试记录
```

任务状态如下：

```text
待处理 → 已分配 → 下载中 → 处理中 → 上传中 → 已完成
                       │
                       └─ 失败 → 等待重试 → 已分配
```

若 Worker 的心跳超时，Controller 会回收其尚未完成的任务并重新进入队列，避免单台机器中断导致任务长期卡住。

## 3. 各组件职责

| 组件 | 主要职责 | 不承担的职责 |
|---|---|---|
| Controller | 任务队列、Worker 鉴权、进度、失败重试、Web 看板 | 不直接处理视频、不做大文件转发 |
| Autoscaler（部署于 Controller） | 读取任务队列和 Worker 状态，调用客户运维脚本启动/停止允许管理的 GPU Worker | 不处理视频、不直接分配任务、不管理未授权主机 |
| GPU Worker | 领取任务、下载、调用算法、上传成品、上报状态 | 不保存全局队列、不调度其他 Worker |
| 对象存储 | 保存源视频与处理结果；向 Worker 提供受限下载/上传地址 | 不进行算法处理和任务调度 |
| Ansible | 初始化系统、同步代码、安装依赖、配置 systemd、批量升级 | 不参与每个视频的实时调度 |

## 4. 为什么视频不经过 Controller

Worker 直接连接对象存储，而不是“Controller 下载后再转发给 Worker”。这样可以：

- 避免 Controller 成为带宽瓶颈；
- 多台 Worker 可以并行下载和上传，扩容更直接；
- 降低控制机磁盘占用与故障影响范围；
- 让视频数据始终在客户指定的存储体系中流转。

Controller 只保存任务元数据，例如源文件对象标识、算法参数、处理状态、Worker 信息、输出对象标识、校验值和错误原因。

## 5. Autoscaler：按需启动和停止 GPU Worker

Autoscaler 是 Controller 机器上的独立常驻服务。它访问 Controller 的任务队列和 Worker 状态，并调用客户已有、经授权的云主机运维脚本管理 GPU Worker 的启停；它不直接操作视频数据，也不参与实时任务分配。

```text
Controller 任务队列 + Worker 状态
               │
               ▼
     Controller 同机 Autoscaler（周期检查）
               │
     仅针对明确允许的私网 IP / 主机池
               │
        调用受控的启动、停止、状态刷新脚本
               ▼
      云端 GPU Worker：启动 → 注册 → 领取任务
                         空闲达到阈值 → 停止
```

当前策略采用保守的伸缩方式：

- 新任务先给予已运行 Worker 领取任务的缓冲时间；队列仍有积压时，才逐台启动 GPU Worker；
- 只管理配置清单中明确列出的 Worker 私网 IP 和对应处理槽位，避免影响其他云主机；
- Worker 启动后需要完成注册并上报状态，再参与任务处理；
- 仅当某台机器的所有已注册槽位均处于空闲状态、队列为空且空闲时间达到阈值时，才允许停止该机器；
- 启动和停止均设有冷却时间与单次操作数量上限，避免重复请求和频繁抖动；
- Autoscaler 记录状态变化和启停事件，便于客户运维审计。

Autoscaler 可根据客户的成本与时效目标配置最小保留运行主机数、队列等待阈值、空闲关机阈值及每次检查的最大启停数量。未启用该服务时，Worker 仍可由客户手动或通过既有云运维系统管理。

## 6. Ansible 的作用：标准化、可重复部署

项目内的 `ansible/` 为 Controller 和 GPU Worker 提供独立角色。一次执行部署清单即可完成对应机器的配置；重复执行会以目标配置为准更新服务，适用于扩容、升级和故障机器替换。

```text
运维人员
   │ 执行 Ansible Playbook（SSH）
   ▼
Controller：部署源代码、Python 环境、Controller 与 Autoscaler 服务、可选看板代理
Worker：部署源代码、CUDA/推理依赖、Worker 槽位服务、GPU 自检
```

当前自动化覆盖的重点包括：

- Controller 从受控代码仓库拉取指定版本，并通过 rsync 向 Worker 推送运行文件；
- 安装 Python、FFmpeg 和运行依赖；
- 为 GPU Worker 执行 CUDA 人脸处理环境初始化，并在需要时处理驱动安装后的重启；
- 为每个 Worker 槽位创建独立的 systemd 常驻服务和工作目录；
- 在 Controller 预注册 Worker 身份，再启动 Worker 服务；
- 将 Controller、Worker 的访问令牌放在 Ansible Vault 等密钥管理机制中，而非写入代码库；代码仓库通过公开 GitHub HTTPS 地址读取；
- 可选配置 Nginx 作为任务看板入口，并使用 Basic Auth 保护；
- 部署并配置与 Controller 同机运行的 Autoscaler；启用后校验主机池、受控运维脚本、槽位容量和安全时间阈值。

Worker “槽位”表示一条独立的任务处理进程。每个槽位同一时间处理一个视频；同一台 GPU 是否配置多个槽位，应以实际显存、视频分辨率和压测结果决定。

## 7. 网络与安全建议

建议在客户 VPC 或等价的私有网络中部署：

| 流量方向 | 建议 |
|---|---|
| Worker → Controller | 仅允许 Worker 网段访问 Controller 服务端口；Worker 主动发起连接 |
| Worker → 对象存储 | 使用临时授权 URL 或实例角色，最小化源视频读取和结果写入权限 |
| 管理员 → 看板 | 经 VPN、堡垒机或受认证的 Nginx 入口访问 |
| Ansible → 主机 | 仅从受控运维节点经 SSH 访问；使用专用密钥 |
| Autoscaler → 云资源控制脚本 | 仅允许固定的启动、停止和状态刷新脚本；仅可管理白名单中的 Worker 私网 IP |

不要将 Controller 的任务接口直接暴露到公网。生产环境建议为看板配置 HTTPS、访问认证和网络访问控制；令牌、部署密钥和云凭据只保存在客户的密钥管理或 Ansible Vault 中。Autoscaler 应以最小权限运行，只能执行固定的客户运维脚本，且脚本的目标应受主机白名单约束。

## 8. 存储与部署模式

| 模式 | 用途 | 说明 |
|---|---|---|
| 本地目录模式 | 单机联调、验收测试 | Controller 与 Worker 可使用同一台测试机的本地目录；不适用于跨机器生产调度 |
| S3 兼容对象存储模式 | 推荐生产模式 | 支持 AWS S3，也可对接具备 S3 兼容接口的客户存储；Worker 直传直取 |

生产部署需要由客户提供或确认：对象存储桶及区域、源视频和结果路径规范、访问授权方式、私网与安全组规则、Controller/Worker 主机规格，以及 Autoscaler 使用的主机池、受控 Worker 白名单、启停运维脚本和伸缩阈值。

当源桶内使用多级目录时，输出桶会保留源前缀之后的相对目录，避免不同目录下的同名视频相互覆盖。例如，源对象 `source/inbox/s/s/m.mp4` 在输出前缀为 `outputs/` 时，结果对象为 `outputs/s/s/masked_m.mp4`。

S3 自动入队可由 Controller 管理工具暂停或恢复。暂停只会停止扫描和创建新任务；已入队任务仍可由 Worker 正常领取、处理和上传，恢复后会继续按当前扫描规则发现新对象。

## 9. 可用性与扩容边界

- Worker 可横向增加，新增机器通过 Ansible 部署并注册后即可开始领取任务；启用 Autoscaler 后，已纳入白名单的云主机可按队列需求自动启动。
- 单 Controller 使用 SQLite WAL 管理任务状态，适合当前的中小规模 Worker 集群（例如十余台机器）的任务领取和状态写入。
- 当客户需要跨地域部署、极大规模并发或 Controller 高可用时，建议将任务数据库和控制服务升级为高可用组件，并在项目实施阶段进行容量设计。
- 实际吞吐量取决于视频分辨率、帧率、时长、场景复杂度、检测参数、GPU 型号、GPU 显存和网络带宽，应以客户样片压测为准。
